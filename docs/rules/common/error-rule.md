# エラー設計ルール

# 基本方針

- エラー形式を統一する
- ユーザ向けメッセージを返却する
- システム内部情報を返却しない
- エラーコードで制御する

---

# エラーコード形式

- `E_XXX` 形式とする

## 例

E_001  
E_101

---

# エラー分類

|範囲|用途|
|---|---|
|E_001〜099|認証|
|E_100〜199|入力|
|E_200〜299|業務|
|E_900〜999|システム|

---

# APIエラーレスポンス

```json
{
  "success": false,
  "data": null,
  "errors": [
    {
      "code": "E_101",
      "message": "ユーザIDは必須です"
    }
  ]
}
```

---

# エラーメッセージ

## OK

ユーザIDは必須です

## NG

SQL Error  
NullReferenceException

---

# ログ出力

以下を出力する

- request_id
- endpoint
- method
- stacktrace
- user_id

---

# フロント制御

- エラーコードで分岐する
- メッセージ文字列比較禁止
- console.errorのみで終了禁止

---

# 例外処理

- 未処理例外禁止
- 共通ExceptionHandler使用
- stacktrace返却禁止

---

# HTTPステータス

|HTTP|用途|
|---|---|
|400|入力エラー|
|401|認証エラー|
|403|認可エラー|
|404|未存在|
|500|サーバエラー|

---

# 禁止事項

- 例外を try-catch で補足したまま記録も再送出もせずに握り潰すこと
- console.log出力のみで動作確認やエラー処理を完了させること
- console.error出力のみでユーザ通知やエラー処理を完了させること
- print出力のみでエラー確認やエラー処理を完了させること
- stacktraceをAPIレスポンスや画面へ返却すること
- エラー応答で success=false を返しながら HTTPステータスコード 200 を返すこと
