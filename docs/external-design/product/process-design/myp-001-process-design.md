# MYP_001 マイページ（組合員情報表示） 処理設計書

## 1. 機能概要

| 項目 | 内容 |
|---|---|
| 機能ID | MYP_001 |
| 機能名 | マイページ（組合員情報表示） |
| 目的/ゴール | 登録済みの組合員情報を表示し、編集モードで住所・連絡先・通知方法・口座登録情報を更新する。 |
| 利用者 | 組合員 |
| 画面/操作トリガー | トップ画面のマイページリンク押下、編集ボタン押下、保存ボタン押下 |
| 入力 | 組合員情報取得要求、編集対象項目、保存操作 |
| 出力 | 組合員情報、更新結果メッセージ、入力エラー、編集/表示モード状態 |
| 前提条件 | ログイン済みセッションが有効であること。 |
| 関連画面 | SCR-004 マイページ画面 |
| 関連IF | IF-006 組合員情報取得、IF-007 組合員情報更新 |

## 2. 入出力データ定義

### 2.1 入力項目

| 項目名 | 型 | 必須 | 制約 | 初期値 |
|---|---|---|---|---|
| postalCode | string | Y | 半角数字 7 桁 |
| address | string | Y | 1..100 文字 |
| phoneNumber | string | Y | 半角数字とハイフン 10..13 文字 |

| X-CSRF-Token | string | Y | サーバー払い出し済みであること |
| X-Request-Id | string | Y | UUID 形式 |

| 項目名 | 型 | 説明 |
|---|---|---|
| userCode | string | 組合員コード |
| userName | string | 組合員名 |
| userNameKana | string | フリガナ |
| birthDate | string | 生年月日 |
| postalCode | string | 郵便番号 |
| address | string | 住所 |
| phoneNumber | string | 電話番号 |

### 2.3 画面状態

| 状態 | 内容 |
|---|---|
| loading | フォームスケルトン表示 |
| view | 読取専用表示 |
| edit | 編集可能状態。保存/キャンセルボタン表示 |
| submitting | 保存 API 呼出中。保存ボタン非活性 |
| success | 更新後値を view 状態で再表示 |
| error | エラー表示。edit 状態を維持 |

## 3. 正常系処理フロー

### 3.1 初期表示

1. 組合員がトップ画面からマイページリンクを押下する。
2. UI は GET /api/v1/users/me を送信する。
3. UserController はセッションを検証し、ログイン中組合員を特定する。
4. UserService は UserRepository.users から組合員情報を取得する。
5. UserController は組合員情報を返却する。
6. UI は view 状態で各項目を表示する。

### 3.2 編集開始

1. 組合員が編集ボタンを押下する。
2. UI は edit 状態へ切り替え、編集可能項目のみ入力可とする。
3. 組合員コード、組合員名、フリガナ、生年月日、出資金残高は読取専用のままとする。

### 3.3 更新

1. 組合員が編集項目を入力し、保存ボタンを押下する。
2. UI は必須・形式チェックを実施する。
3. 入力チェック OK の場合、UI は PUT /api/v1/users/me を送信する。
4. UserController はセッションと CSRF トークンを検証する。
5. UserController は RequestValidationService で必須・形式・文字数チェックを再実施する。
6. UserService は UserRepository.users から現在データを取得し、本人データであることを確認する。
7. UserService は更新対象項目のみ差分更新データを作成する。
8. UserService は UserRepository.users を更新する。
9. UserService は更新後の組合員情報を再取得し、レスポンスを返却する。
10. UI は success メッセージを表示し、view 状態へ戻して最新情報を再表示する。

### 3.4 キャンセル

1. 組合員がキャンセルボタンを押下する。
2. UI は未保存入力値を破棄する。
3. UI は最後に取得済みの組合員情報で view 状態へ戻る。

### 3.5 トランザクション境界

| 境界 | 内容 |
|---|---|
| TX-01 | 初期表示は参照トランザクション |
| TX-02 | `users` の更新を 1 トランザクションで実施する |
| TX-03 | 更新後再取得は別参照トランザクション |

## 4. 例外/エラー処理

### 4.1 入力エラー

| エラーコード | 検知条件 | 表示内容 | 復帰方法 |
|---|---|---|---|
| E_101 | postalCode、address、phoneNumber、email 未入力 | 各項目下に必須メッセージ表示 | 入力後に再実行 |
| E_102 | 郵便番号桁数不正、電話番号形式不正、メール形式不正、文字数超過 | 各項目下に形式エラー表示 | 入力値修正後に再実行 |

### 4.2 認証・認可・業務エラー

| エラーコード | 検知条件 | 表示内容 | 復帰方法 |
|---|---|---|---|
| E_001 | セッション無効、タイムアウト | 「セッションの有効期限が切れました」を表示して SCR-001 へ遷移 | 再ログイン |
| E_002 | 他組合員データ更新要求 | 403 相当の共通エラー表示 | 正常な画面遷移から再表示 |
| E_201 | 更新対象が既に無効、更新不可状態 | 画面上部に業務エラー表示 | 再取得後に再編集 |

### 4.3 システムエラー

| エラーコード | 検知条件 | ユーザー通知 | 処理 |
|---|---|---|---|
| E_901 | 取得失敗、更新失敗、DB 障害、タイムアウト | 画面上部に「時間をおいて再度お試しください」を表示 | 保存ボタンを再活性化し、edit 状態を維持する |

## 5. データ更新・整合性

| 項目 | 内容 |
|---|---|
| 参照データ | `users` |
| 更新データ | `users` の postal_code、address、phone_number、email、notification_method、bank_account_info、updated_at |
| 使用 Repository | UserRepository |
| 更新順序 | 1. 本人確認 2. 現在値取得 3. 差分作成 4. 更新 5. 更新後再取得 |
| 整合性ルール | 読取専用項目は更新対象に含めない |
| 冪等性 | 同一内容を再送した場合、最終状態が同一であれば成功扱いとする |
| 排他 | 楽観ロックで updated_at または version を確認し、競合時は再編集を促す |

## 6. ログ/監査/運用観点

| 観点 | 内容 |
|---|---|
| 操作ログ | request_id、endpoint、method、user_code、更新対象項目、結果 |
| 監査ログ | user_code、更新日時、変更項目一覧 |
| エラーログ | request_id、例外内容、stacktrace |
| マスキング | 口座番号、生メールアドレスはログでマスクする |
| 性能観点 | 取得は 10 秒以内、更新は 15 秒以内を目標とする |

## 7. 前提・要確認事項

- 前提: 通知方法は単一選択のラジオボタン形式とし、`0` は「通知しない」、`1` は「SMSで通知」とする。
- 要確認: 住所入力の郵便番号連携自動補完要否。
- 要確認: 口座登録情報の入力粒度を自由記述ではなく構造化項目へ分割するか。
