# 設計プロンプト

## 概要

このプロンプトは、GitHub Copilot や他の生成AIを使用してシステム設計を支援するためのテンプレートです。

## アーキテクチャ設計プロンプト

```
以下の要件に基づいてシステムアーキテクチャを設計してください。

【要件】
（docs/requirements.md の内容を貼り付けてください）

【出力形式】
- システム構成図（テキスト形式）
- 各コンポーネントの役割説明
- データフロー
- 使用する技術スタックの推奨と理由
```

## API 設計プロンプト

```
以下の機能要件に基づいて REST API を設計してください。

（設計する機能の要件を記述してください）

【出力形式】
- OpenAPI 3.0 形式の YAML
- 各エンドポイントの説明
- リクエスト/レスポンスのスキーマ定義
```

1) 画面/フロントエンド ⇄ バックエンドAPI（REST等）
2) バックエンド ⇄ 外部システムAPI（決済、認証、基幹、メール、ファイル保管等）

- 画像イメージに登場する連携先/データフローがあれば必ず反映する
- 不明点は勝手に決めず、必ず「前提」または「要確認事項」として明示する
- 可能な限り、インタフェースごとに以下の観点を具体化する：
  - 認証/認可（例：JWT/OAuth2/API Key/セッション等）※要件に沿う
  - 監査ログ/トレーシング（相関ID等）
  - エラー設計（HTTPステータス、業務エラーコード、メッセージ、リトライ可否）
  - 非機能（タイムアウト、リトライ、冪等性、レート制限、同時実行、データ量上限）
  - バージョニング（必要なら）
  - セキュリティ（PII、暗号化、マスキング、CSRF/CORS等）※要件に沿う

## API一覧

あなたは業務Webアプリケーションのバックエンド/API設計者です。

インタフェース設計書に定義されているIF-ID/API仕様を正として、機能一覧の各機能がどのAPIを利用するか対応付けた一覧にしてください。

- #file:glossary.md

2) 各APIについて、最低限以下を確定/整理（未確定は「案」または「要確認」で分離）：

- 命名は資料内の表記に合わせて統一する（機能名、用語、略語）

## 処理設計

```
あなたは業務Webアプリケーションのアプリケーション設計者です。

処理設計書は、機能単位でファイル分割して作成し、各機能の処理詳細（正常系/例外系/入力チェック/状態遷移/データ更新/トランザクション/排他/ログ）を実装できる粒度で記載してください。

# インプット
- 画面イメージ（画像 .png）※このpngは私がCopilot Chatに直接添付します。添付された画像内容（登場人物・手順・分岐・例外）を読み取って反映してください。
- 要件定義書（.md）: #file:requirements.md 
- 機能一覧（.md）: #file:function-list.md 

# ルール
以下のルールを必ず遵守してください（命名、用語、エラー表現、例外時の流れ）:
- #file:naming-rule.md 
- #file:error-rule.md 
- #file:glossary.md 
- #file:screen-design-rule.md 

# 作成対象（必須）
- function-list.md に記載の各機能（機能IDがある場合はそれをキーにする）について、
  「処理設計書（1機能=1ファイル）」を作成する。
- 出力は “ファイルごとに” Markdown本文を提示し、先頭に作成すべきファイルパスを明記すること。

# ファイル作成ルール（必須）
- 出力するファイルパスは以下の命名規則で提示する（機能IDが無い場合は機能名を英語スラッグ化）：
  - <<FUNCTION_ID>_.md
  例）FN-001_process-design.md

# 前提（業務Web）
- Web画面操作をトリガーとして処理が開始する想定（クリック、入力確定、初期表示など）
- 一覧/検索/登録/更新/削除などの一般的な業務Webパターンを考慮
- 不明点は推測で断定せず「前提」「要確認事項」に分離する

# 設計書に必ず含める内容（機能ごと：必須）
各機能の処理設計書には以下を必ず含める：

1) 機能概要
- 機能ID/機能名（function-list.mdの記載をそのまま）
- 目的/ゴール
- 利用者（ロールが読み取れれば）
- 画面/操作トリガー（PNGから読み取れれば）
- 入力/出力（ユーザー入力・画面表示）
- 前提条件（ログイン/権限/状態）

2) 入出力データ定義（粒度は“実装で迷わない”レベル）
- 入力項目：名称、型、必須、制約（桁/形式/範囲/相関）、初期値
- 出力項目：表示項目/返却項目（一覧列やメッセージ等）
- 画面状態（選択状態、ページング条件、検索条件保持など）※該当時

3) 処理フロー（正常系）
- 手順を番号付きで詳細化（UI→入力チェック→処理→更新→結果表示）
- 分岐条件があれば明記（条件/結果）
- 画面遷移があれば明記（遷移先/遷移条件）
- トランザクション境界（開始/コミット/ロールバックの単位）を明記（想定でよいが要確認に分離可）

4) 例外/エラー処理（必須）
- 入力エラー（バリデーションNG）：どの項目で何を表示し、処理はどう戻るか
- 業務エラー（例：在庫不足、重複、状態不整合など）：検知条件と画面への返し方
- システムエラー（例：タイムアウト、依存サービス障害など）：リトライ可否、ユーザー通知、ログ
- セッション切れ/権限不足：どう遷移させるか（ログイン画面誘導、403表示など）

5) データ更新・整合性
- 参照/更新するデータ（エンティティ/テーブル/概念名。資料に無ければ概念でOK）
- 更新順序、整合性ルール、同時更新時の扱い（楽観/悲観ロックなど必要なら）
- 冪等性（登録/更新/削除など）：二重送信時の挙動

6) ログ/監査/運用観点（必要最低限でOK）
- 操作ログ/監査ログに残す項目（ユーザー、機能、対象ID、結果、エラーなど）
- 障害時に必要な情報（相関IDなど、資料にあれば反映）
- 性能観点（一覧取得のページング、検索条件、上限など、必要そうなら）


# 出力形式（必須）
- Markdownファイルで出力する
- フォーマットとして、#file:fm_process_design.md を参照してください。

## DB設計
```
あなたは業務Webアプリケーションのデータベース設計者です。
以下のER図（エンティティ一覧・ER図）をインプットとして読み取り、「DB設計書（物理設計）」を作成してください。

# インプット
- ER（.md）:#file:er_diargram.md
    
# ルール
以下のルールを必ず遵守してください（命名、用語、エラー表現、例外時の流れ）:
- #file:naming-rule.md 
- #file:error-rule.md 
- #file:glossary.md 
- #file:screen-design-rule.md 

# 作成対象（必須）
ER図の情報をもとに、物理DB設計として以下を具体化してください：

1) テーブル一覧
2) テーブル定義（カラムレベルまで詳細化）
3) 制約定義（PK / FK / UNIQUE / CHECK）
4) インデックス設計（検索性能を考慮）
5) DDL（CREATE TABLE文：代表例でOK）
6) 設計方針
7) 前提・要確認事項

# 設計ルール（重要）
- ER図のエンティティをベースに「テーブル」を定義する
- リレーションをもとに外部キー（FK）を設計する
- N:M関係は中間テーブルとして物理設計する
- 不明な情報（型、桁数、制約など）は推測せず、「案」として提示し要確認に記載する
- 業務Web一般設計として、以下を考慮する：
  - 監査カラム（created_at, created_by, updated_at, updated_by）
  - 論理削除（deleted_flag / deleted_at）※必要と判断した場合
